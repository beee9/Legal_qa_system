# Legal QA System 项目面试讲解指南

## 1. 项目概述 (1-2分钟)

### 背景与目标
我在实习期间负责开发了一个**智能法律问答系统**，主要解决两个痛点：
1. **传统法律咨询效率低** - 用户需要预约律师，等待时间长，成本高
2. **法律条文检索困难** - 2500+条法律条文，普通用户很难快速定位相关法条

**系统目标**：通过AI技术实现7×24小时在线法律咨询，自动检索相关法条并生成专业答案。

### 核心功能
- **智能问答**：用户提问后，系统自动检索相关法条并生成法律建议
- **多轮对话**：针对劳动纠纷等场景，系统会主动追问缺失信息（如是否签合同、工作地点）
- **实时流式输出**：答案逐字返回，提升用户体验
- **会话管理**：支持多轮对话上下文保持和历史记录查询

### 技术栈选型与理由

**后端框架**: FastAPI
- 选型理由：原生支持异步、WebSocket，性能优于Flask
- 自动生成OpenAPI文档，便于前后端协作

**AI框架**: LangGraph
- 选型理由：状态机式的对话流程管理，比LangChain更灵活
- 可视化节点编排，便于调试复杂对话逻辑

**向量模型**: BGE-M3
- 选型理由：支持dense + sparse双模态向量，召回效果比单一向量好20%+
- 支持中文语义理解，适合法律领域

**向量数据库**: Milvus
- 选型理由：专为向量检索优化，QPS比Faiss高3倍
- 支持混合检索（dense + sparse），符合BGE-M3输出

**缓存**: Redis
- 用途1：会话状态管理 (key: session_id, value: 对话上下文JSON)
- 用途2：热点问题缓存 (key: query_hash, value: answer)
- 效果：热点问题命中率80%+，响应时间从2.5s降至0.3s

## 3. 核心模块详解 (5-7分钟)

### 3.1 混合检索模块

**问题**：单纯的向量检索在精确匹配场景下效果差（如用户问"第82条是什么"）

**解决方案**：BM25 + 向量检索混合策略

#### 检索流程
```python
def search(query):
    # 1. 先用BM25做关键词匹配
    bm25_score, bm25_result = bm25_search(query)
    
    # 2. 根据阈值决定是否需要RAG
    if bm25_score > 6.0:  # 精确匹配
        return bm25_result, False
    else:  # 模糊查询，需要向量检索
        return vector_search(query), True
```

#### 技术亮点
- **BM25**: 基于TF-IDF的关键词匹配，擅长精确查询（如法条号、关键词）
- **向量检索**: BGE-M3语义理解，擅长模糊查询（如"拖欠工资怎么办"）
- **阈值路由**: 6.0是经过实验调优的阈值，平衡准确率和召回率

#### 数据支撑
- BM25命中率：35%（精确查询场景）
- 向量检索命中率：65%（语义查询场景）
- 混合策略准确率：提升40%（相比单一向量检索）

**解决方案**：基于LangGraph设计6节点状态机

#### 关键节点实现

**1. 意图分类节点**

def classify_intent(state):

    # 对话结束检测

    # 法条查询
    if re.search(r"第\s*\d+\s*条", query):
        return {"intent": "法条查询"}
    
    # 法律咨询
    return {"intent": "法律咨询"}

**2. 事实澄清节点**（核心难点）
```python
def clarify_facts(state):
    query = state["query"]
    clarified = state.get("clarified_facts", {})
    missing_info = []
    
    # 劳动纠纷场景
    is_labor = "工资" in query or "labor_contract" in clarified
    if is_labor:
        # 先从query提取信息（避免重复追问）
        if re.search(r"签了|肯定签", query):
            clarified["labor_contract"] = "已签订"
        if re.search(r"1万5|(\d+)万", query):
            clarified["amount"] = query
        if re.search(r"深圳|北京|上海", query):
            clarified["location"] = match.group(0)
            
        # 检查还缺少哪些信息
        if "labor_contract" not in clarified:
            missing_info.append("是否签订书面劳动合同？")
        if "amount" not in clarified:
            missing_info.append("拖欠金额是多少？")
        if "location" not in clarified:
            missing_info.append("工作地在哪个城市？")
    
    return {"missing_info": missing_info, "need_clarify": len(missing_info) > 0}
```

**3. 答案生成节点**
```python
def generate_answer(state):
    clarified = state["clarified_facts"]
    
    if clarified.get("labor_contract") == "已签订":
        # 已签合同 → 主张拖欠工资 + 赔偿金
        amount = extract_amount(clarified["amount"])  # "1万5" → 1.5
        location = clarified["location"]
        
        answer = f"""
根据《劳动合同法》第30条、第85条，您可以主张：
1. 拖欠工资约{amount}万元
2. 赔偿金{amount*0.5}-{amount}万元（按应付金额50%-100%计算）

维权步骤：
1. 向{location}劳动监察大队投诉（12333）
2. 或直接申请劳动仲裁
3. 紧急情况可向法院申请支付令
        """
    elif clarified.get("labor_contract") == "未签订":
        # 未签合同 → 主张双倍工资 + 拖欠工资
        answer = """
根据《劳动合同法》第82条，您可以主张：
1. 双倍工资差额（最多11个月）
2. 拖欠工资
3. 经济补偿金
        """
    
    return {"draft_answer": answer}
```

#### 技术亮点
- **状态持久化**: Redis存储`state`，支持断点续答
- **条件路由**: `need_clarify` 决定是追问还是继续检索
- **信息累积**: `clarified_facts` 逐轮累积用户补充的信息

**问题**：生成长答案时，用户需要等待2-3秒才能看到内容

### 3.4 边界场景优化

在测试中发现10+个边界场景问题，逐一优化：

#### 问题1：否定回答误识别
- **现象**: 用户说"没有签合同"，系统识别为"已签订"
- **原因**: 正则 `r"有签"` 匹配了"没**有签**合同"
- **解决**: 
  - 否定判断优先于肯定判断
  - 使用负向断言 `r"(?<!没)有签"`

#### 问题2：口语化数字不识别
- **现象**: "1万5"被识别为"1万"
- **原因**: 正则只匹配 `r"(\d+)万"`，后面的"5"被忽略
- **解决**: 新增正则 `r"(\d+)万(\d+)"` → 解析为 `万 + 千/10`

#### 问题3：不完整回答直接生成答案
- **现象**: 用户只回答"签了"，系统没有继续追问地点和证据
- **原因**: `clarify_facts()` 只检查当前query，没检查对话上下文
- **解决**: 新增判断条件 `is_labor = "工资" in query or "labor_contract" in clarified`

#### 问题4：地区显示错误
- **现象**: 用户说"北京"，答案显示"深圳市劳动监察"
- **原因**: 答案模板硬编码了"深圳"
- **解决**: 改为变量 `f"{location}劳动监察"`

**测试覆盖的边界场景**：
- ✅ 否定回答（"没有签"）
- ✅ 不完整回答（"签了"）
- ✅ 反问句（"肯定签了啊"）
- ✅ 口语化数字（"1万5"、"一万多"）
- ✅ 情绪化表达（"老板太过分了"）
- ✅ 中途放弃（"算了不想问了"）
- ✅ 一次性给全信息
- ✅ 模糊金额（"好几万"）

## 5. 性能优化 (2分钟)

### 优化点1：Redis热点缓存
- **策略**: 对query做MD5哈希，缓存高频问题的答案
- **效果**: 热点问题命中率80%，响应时间0.3s

### 优化点2：向量检索优化
- **问题**: 全库2542条法条检索，QPS只有20
- **优化**: 
  - Milvus IVF索引（nlist=128）
  - Top-K限制为3（实验发现Top-5收益不大）
- **效果**: QPS提升到80+

### 优化点3：WebSocket连接池
- **问题**: 50+并发连接时出现阻塞
- **优化**: 
  - 使用asyncio异步处理
  - 每个连接独立事件循环
- **效果**: 支持100+并发

### 优化点4：BM25索引预加载
- **问题**: 每次查询都重建BM25索引，耗时200ms
- **优化**: 服务启动时预加载到内存
- **效果**: BM25查询降至10ms

## 8. 可能的追问及回答

### Q1: 为什么不用LangChain而用LangGraph？
**A**: LangChain更适合线性的RAG流程，而我们的场景需要条件分支（如是否追问、是否需要向量检索），LangGraph的状态机模式更灵活。而且LangGraph的可视化节点图便于调试复杂流程。

### Q2: BGE-M3的dense和sparse向量是怎么用的？
**A**: 
- **Dense向量**（1024维）：捕捉整体语义，适合模糊查询
- **Sparse向量**：保留关键词信息，适合精确匹配
- **混合检索**：Milvus同时检索两种向量，取加权平均分
- **效果**：比单一dense向量召回率提升15%

### Q3: Redis缓存的过期策略是什么？
**A**: 
- **会话状态**：30分钟TTL，用户无操作自动过期
- **热点答案**：24小时TTL，每天凌晨刷新
- **淘汰策略**：allkeys-lru（内存不足时淘汰最久未使用的key）

### Q4: 如果法律条文更新了怎么办？
**A**: 
1. MySQL存储法条时记录`status`字段（现行有效/已废止）
2. 定期运行脚本同步最新法条
3. 重新向量化并更新Milvus索引
4. 清空Redis缓存，避免返回过期答案

### Q5: 怎么保证生成答案的准确性？
**A**: 
1. **答案审查节点**：检查是否引用法条、是否有已废止法律
2. **模板化生成**：核心逻辑用模板，减少LLM幻觉
3. **免责声明**：自动添加"仅供参考，不构成法律意见"
4. **人工复核**：定期抽查生成答案质量

### Q6: 如果用户问的问题数据库没有怎么办？
**A**: 
1. 向量检索会返回最相似的法条（即使不完全匹配）
2. 如果相似度得分低于阈值（0.6），返回"暂无相关法条，建议咨询专业律师"
3. 记录这类query，后续补充数据

### Q7: 系统的并发能力如何？
**A**: 
- 单机支持100+并发WebSocket连接
- 瓶颈在向量检索（Milvus QPS 80）
- 优化方向：
  - Redis缓存提升命中率
  - Milvus集群部署
  - 应用层水平扩展（负载均衡）

### Q8: 为什么不用大模型直接生成答案？
**A**: 
1. **成本**：每次调用GPT-4成本0.03元，QPS 100时每天需2592元
2. **准确性**：大模型可能产生幻觉，引用不存在的法条
3. **时效性**：大模型训练数据截止日期较早，法律更新后无法及时响应
4. **我们的方案**：RAG + 模板生成，既保证准确性又控制成本
