## 一、团队协调类问题

### [P-01] AI 队友"卡死"无响应
- **问题**：数据库工程师被唤醒后长时间无产出（磁盘无新文件），消息、任务指派均无法唤醒，最后连下线请求都无法确认，只能强制移除。
- **原因**：队友之前被手动中断（user_stop）后回合状态异常，无法恢复执行。
- **解决**：`team_shutdown_agent` 下线 + 重新派发给其他队友（后端工程师接手）。
- **教训**：队友若被手动中断后无响应，尽早判定异常并换人/重启，不要反复等待。

### [P-02] 误判队友"没在干活"
- **问题**：以为后端工程师 / QA 没产出，Leader 擅自接手执行，结果与队友的工作互相覆盖（CSV 数据冲突）。
- **原因**：检查时机太早——队友生成文件的时间晚于我检查的时间点，误以为无进展。
- **解决**：核查文件修改时间戳、队友状态（working/idle）后再判断；发现冲突后停止重复劳动，协调整合。
- **教训**：队友执行慢≠不动。应以「文件产出时间 + 队友状态」双重判断，Leader 接手前务必确认队友是否在推进。

### [P-03] Leader 与队友重复劳动导致数据冲突
- **问题**：Phase 1-2 的 legal_qa.csv 被 build 脚本（Leader）和 generate_legal_qa.py（队友）多次互相覆盖，数据源混乱。
- **解决**：权威重建——用两个可靠来源（精确查询类从 legal_data 提取 + 概念类由 generate_legal_qa.py 生成）合并去重，清空重导。
- **教训**：数据类任务应明确唯一责任方和统一数据源，避免多人并行写同一文件。

## 二、环境与基础设施问题

### [P-04] Docker 服务未就绪 / MySQL 容器不自启
- **问题**：MySQL/Redis/Milvus 端口未开放，Docker 引擎未启动；MySQL 容器 `restart=no`，引擎重启后不自启。
- **解决**：启动 Docker Desktop + `docker compose up -d`；`docker update --restart always mysql_container`。
- **教训**：容器配置 `restart=no` 会在重启后丢服务，关键服务应设 `restart=always`。

### [P-05] Milvus/etcd 磁盘 I/O 错误崩溃
- **问题**：etcd、Milvus standalone 报 `input/output error` 崩溃（`write /etcd/data/...: input/output error`）。
- **原因**：Docker Desktop 启动初期文件共享（gRPC-FUSE）未就绪的临时 I/O 错误，非配置问题。
- **解决**：重新 `docker start` / `docker compose up` 后恢复正常。
- **教训**：Windows Docker Desktop 刚启动时挂载卷可能 I/O 异常，重试即可，勿误判为配置损坏。

### [P-06] 缺 embedding 环境（torch/pymilvus/FlagEmbedding）
- **问题**：项目 .venv、系统 python、Anaconda 均缺 torch/pymilvus；E:\python 只有 CPU 版 torch。
- **解决**：用 E:\python（有 torch 2.8）+ 补装 pymilvus、milvus-model、FlagEmbedding。
- **教训**：环境依赖是队友执行卡住的常见根因，Leader 应优先排查运行环境。

### [P-07] torch 为 CPU 版，无法 GPU 训练
- **问题**：E:\python 的 torch 是 `2.8.0+cpu`，`torch.cuda.is_available()=False`。
- **解决**：GPU 训练需另建独立环境装 CUDA 版 torch（`--index-url https://download.pytorch.org/whl/cu126`），见 `requirements-train.txt`。
- **教训**：本机有 RTX 3060（6GB）但默认环境是 CPU 版，训练前需明确 CUDA 版 torch。

### [P-17] torch CUDA 下载：官方源连接重置、镜像 pip index 不识别
- **问题**：① pip 从官方源（download.pytorch.org）下载 torch 2-3GB 时 `ConnectionResetError(10054)` 失败；② 改用阿里云 `pytorch-wheels` 作 pip index 报 `Could not find torch==2.7.0`；③ 最终 curl 直下 wheel 可行但速度 ~450KB/s。
- **原因**：官方源国内连接不稳；阿里云 pytorch-wheels 镜像的 pip simple index 结构不完整，pip 无法解析；下载带宽受网络限制。
- **解决**：`curl -L -C - --retry` 断点续传直下 wheel（`https://mirrors.aliyun.com/pytorch-wheels/cu126/torch-...-win_amd64.whl`），完成后 `pip install 本地.whl`。
- **教训**：大文件（>1GB）下载用 curl 断点续传比 pip 可靠；国内环境用阿里云 pytorch-wheels 镜像直下 wheel，勿依赖其 pip index。

### [P-16] conda 创建环境失败（清华镜像 msys2 channel 404）
- **问题**：`conda create` 报 `HTTP 404 for channel anaconda/pkgs/msys2 <mirrors.tuna.tsinghua.edu.cn>`，环境创建失败。
- **原因**：老版本 conda 4.14 解析时请求清华镜像上不存在的 msys2 channel（Anaconda 官方 channel 里 msys2 也只在特定源有）。
- **解决**：放弃 conda，改用 **venv 方案**：`E:/python -m venv .venv-train`（Python 3.9.5，后改名 `.venv-RAGtrain`）+ pip 装 CUDA torch + requirements-train.txt。
- **教训**：老版本 conda 配清华镜像可能遇到 channel 404，venv + pip 方案更可控，适合本机 Python 已就绪的场景。

## 三、数据与检索问题

### [P-08] BM25 检索命中教育数据
- **问题**：清空前 BM25 返回"java：String和char的区别"等教育数据。
- **原因**：BM25Search 从 **Redis 缓存**（`qa_original_questions`）读问题索引，Redis 残留教育时代缓存。
- **解决**：清空 Redis 的 `qa_original_questions`、`qa_tokenized_questions`、`answer:*`。
- **教训**：改造领域时务必清理旧缓存，否则新数据不生效。

### [P-09] BM25 softmax 阈值被问题数量稀释
- **问题**：法条精确查询（"民法典第五百零九条是什么？"）不命中，走 RAG；而库里明明有该问题且 BM25 原始分数很高（14.88）。
- **原因**：2632 个问题做 softmax 归一化后分数被稀释，精确匹配仅 0.017~0.17，达不到原 0.85 阈值。
- **解决**：改用**原始 BM25 分数阈值 6.0**（精确/概念命中原始分 ≥12，无关查询 ≤4，分界清晰），修改 `bm25_search.py` + 两处调用。
- **教训**：softmax 归一化阈值对问题数量敏感，法律场景问题多时应改用原始分数判断。设计文档"提高阈值到 0.88~0.90"的建议与实际不符，实测为准。

### [P-10] 公司法必须用 2023 修订版
- **问题**：公司法多次修订，需确保下载 2023 修订版（2024-07-01 施行，266 条）而非旧版。
- **解决**：任务描述明确标注版本，最终文件头含"2023年12月29日...第二次修订"验证通过。
- **教训**：法律数据对版本敏感，必须锁定最新修订版并验证版本标识。

## 四、代码与 API 兼容问题

### [P-11] pymilvus 3.0 API 差异
- **问题**：`add_collection_field()` 参数名从 `datatype` 改为 `data_type`；建集合推荐用 Schema 方式；IVF_FLAT 索引缺 `nlist` 参数报错。
- **解决**：改用 `create_schema()` + `add_field()` + `create_collection(schema=...)`；索引加 `params={"nlist": 128}`。
- **教训**：pymilvus 3.x API 变化大，按新版本推荐用法写。

### [P-12] milvus_model 与 flag_embedding 兼容 bug
- **问题**：`BGEM3EmbeddingFunction` 对单条 query 报 `'str' object has no attribute 'values'`（sparse 处理错误）。
- **原因**：milvus_model 0.2.12 与 flag_embedding 1.4.0 的 sparse 输出格式不兼容。
- **解决**：入库用 dense-only 规避；检索用底层 `BGEM3FlagModel` 直接取 dense。
- **教训/隐患**：⚠️ Phase 4 集成若 vector_store 用 hybrid 检索会触发此 bug，届时需改用底层 API 或调整 flag_embedding 版本。

### [P-13] Windows 控制台 GBK 中文乱码
- **问题**：脚本 print 中文时终端显示乱码（`�½�` 等）。
- **原因**：Windows 控制台默认 GBK 编码，Python 输出 UTF-8 中文时显示错乱。
- **解决**：仅影响终端显示，文件本身 UTF-8 正确。用 repr/hexdump 验证，勿误判数据损坏。
- **教训**：Windows 下区分"显示乱码"与"数据乱码"，验证要基于文件内容而非终端。

## 五、数据质量与流程问题

### [P-14] 法条条文提取有交叉引用误差
- **问题**：按"第X条"切分条文时，正文中的交叉引用（"参见第九百九十九条"）被误判为条文，民法典 1322>1260。
- **解决**：改正则只匹配**行首**的条号（`(?:^|[\r\n])\s*(第...条)`），精确到 1260 条。
- **教训**：文本解析要结合文档结构特征（行首/段落边界），避免误匹配。

### [P-15] 精确查询类 95 条重复问题
- **问题**：从 txt 提取的精确查询类有 95 条重复（`legal_qa_exact.csv` 2542→去重后 2489）。
- **解决**：合并时 `drop_duplicates(subset=['问题'])`。
- **教训**：自动生成数据后必须做去重校验。

---

### [P-19] 集成阶段问题：vector_store 适配 dense-only 集合（H-01 解决）
- **问题**：① 原 vector_store 用 milvus_model 的 BGEM3EmbeddingFunction（触发 H-01 sparse 兼容 bug）；② 其 schema 期望 dense+sparse+多字段，但 Phase1-3 入库的是 dense-only 集合；③ 模型路径指向新项目（空）而非原项目；④ pymilvus 3.0 search 用 `param` 参数报错（应为 `search_params`）。
- **解决**：重写 vector_store.py → 改用底层 `FlagEmbedding.BGEM3FlagModel`（仅 dense）+ dense-only 检索 + 模型路径指向原项目 models + 适配 legal_rag 字段（subject/text/dense_vector）+ `search_params` 参数。
- **结果**：RAG 检索正常（"合同违约"→《民法典》违约责任条款、rerank 生效）。**H-01 隐患已解决**。
- **教训**：集成时 schema 一致性与模型路径是常见坑；pymilvus 3.0 API 参数名（search_params 而非 param）需注意。

### [P-20] 集成验证结果（Phase 4）
- **端到端四类查询**全部通过：法条精确查询/概念解释/多实体对比/复杂场景咨询 → BM25 层命中准确法律答案（问答库覆盖良好）。
- **意图分类**：query_classifier 三分类预测全部正确（法条查询/法律咨询/通用问题），模型路径已指向 best_model。
- **单元测试**：9/9 通过（BM25 精确匹配、无关查询降级 RAG、阈值边界、Redis 缓存）。

### [P-18] BERT 训练过程问题集（GPU 训练）
- **问题与解决**（Phase 3 训练 chatgpt 改造的 legal_train_bert.py）：
  1. 分类头尺寸不匹配：初始化模型是 2 类，from_pretrained(num_labels=3) 报 `size mismatch` → 加 `ignore_mismatched_sizes=True`（encoder 继承、分类头重建）。
  2. 缺 accelerate：Trainer 报 `requires accelerate>=0.26.0` → `pip install accelerate`。
  3. 数据路径：相对路径 `../classify_data` 基于运行目录（项目根）解析失败 → 改绝对路径。
  4. evaluate target_names 硬编码二分类报错 → 改三类。
  5. **训练极慢（30s/步，90 步约 45 分钟）**：BertClsDataset.__getitem__ 每步重复 tokenize → **改为初始化时预 tokenize**（一次性编码全部样本），训练降到 **37 秒**（train_loss 0.105）。
- **结果**：法律三分类 BERT 训练完成，测试准确率 **100%**（法条查询37/法律咨询16/通用问题7），模型保存至 `rag_qa/core/bert_query_classifier/best_model`。推理验证：法条查询→法条查询、合同违约→法律咨询、你好→通用问题 全部正确。
- **教训**：Trainer 训练时若 DataLoader 每次 __getitem__ 做重 tokenize，CPU 会成为瓶颈，务必预 tokenize；多轮调试（依赖/路径/label）需系统性排查。
